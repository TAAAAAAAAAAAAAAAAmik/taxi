# Маршруты России и сервер сообщений

## Почему нельзя зашивать всю Россию в приложение

Полный адресный граф России: регионы, города, села, улицы, дома, корпуса, дробные номера, подъезды, точки интереса и дорожные маршруты. Это должно жить на сервере и регулярно обновляться из геокодера/картографического провайдера. Мобильное приложение должно хранить только легкий локальный пакет для MVP-зоны и обращаться к серверу по геолокации пользователя.

## Как устроено сейчас

- `src/data/salavatDistrict.ts` содержит детальный локальный пакет для Салаватского района: населенные пункты, улицы, дома-примеры и важные точки.
- В полях "Откуда" и "Куда" поиск умеет подсказывать улицы и дома вроде `Коммунистическая улица, дом 65/1`.
- В заказе есть кнопка "Определить мое место": приложение запрашивает геолокацию и вызывает backend reverse geocode, если внешний URL не задан.
- `scripts/mvp-backend.mjs` отдает серверные MVP endpoint'ы:
  - `GET /geo/address-search?query=...` - адресные подсказки;
  - `GET /geo/reverse?latitude=...&longitude=...` - адрес по координатам;
  - `POST /geo/routes` - расчет расстояния, ETA и цены;
  - `POST /support/messages` и `GET /support/threads` - сервер сообщений;
  - `GET /realtime/ws`, `GET /realtime/stream` и `GET /realtime/snapshot` - WebSocket, SSE и snapshot заказов, уведомлений и обращений.
- `.env.example` содержит адреса внешних провайдеров:
  - `EXPO_PUBLIC_ADDRESS_SEARCH_URL`;
  - `EXPO_PUBLIC_REVERSE_GEOCODE_URL`;
  - `EXPO_PUBLIC_ROUTE_SEARCH_URL`;
  - `EXPO_PUBLIC_MESSAGE_SERVER_URL`.
- Если адрес указывает на `example.com` или не задан, backend использует локальный MVP fallback по Салаватскому району и нескольким межгородным якорям РФ.

## Целевая серверная схема

1. Клиент открывает заказ.
2. Приложение запрашивает геолокацию.
3. Сервер получает координаты и строку поиска.
4. Сервер возвращает ближайшие адреса, дома, подъезды, организации и популярные маршруты.
5. Приложение показывает подсказки, а после выбора маршрута сервер считает цену, расстояние и время.

## Сервер сообщений

Чат поддержки выделен в отдельный экран и отправляет сообщения в MVP backend. При недоступном backend приложение сохраняет сообщение локально и показывает пользователю статус ошибки:

- категории обращений;
- быстрые сообщения;
- история диалога;
- автоответ поддержки;
- отображение режима "MVP сервер сообщений";
- уведомление для админки через realtime snapshot/SSE.

Продакшен-следующий шаг: подключить внешний message broker или managed realtime, роли операторов поддержки и полноценные статусы доставки/прочтения.

## Проверка

```bash
npm run test:geo-messaging
```

Smoke-тест поднимает временный backend, проверяет адресный поиск, reverse geocode, расчет маршрута, создание support thread и наличие обращения в realtime snapshot.

## Что важно для бизнес-модели доступа

Если водитель оплачивает подписку или выбирает комиссию 7%, сервис должен подтверждать ценность реальным потоком заказов. Поэтому маршруты и геолокация должны работать не как статичный справочник, а как трафиковая система: где пользователь находится, какие поездки рядом, сколько водителей доступно и как быстро заказ будет принят.
