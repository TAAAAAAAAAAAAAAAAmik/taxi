# Runbook закрытого rehearsal-пилота

Этот runbook описывает первый Android APK-пилот без боевого VPS, ИП и платежных систем. Backend работает локально или в LAN, доступ водителей включается вручную во встроенной админке.

## 1. Подготовка

- Подготовить APK env: `npm run prepare:pilot-apk`. Скрипт сам подставит LAN-IP в `eas.json`; если нужно вручную, задайте `PILOT_API_HOST=<LAN-IP>`.
- Запустить backend без SMS: `npm run backend:pilot`.
- Проверить `http://<LAN-IP>:3100/health` с телефона в той же сети.
- Собрать APK профилем `pilot-apk`.
- Убедиться, что `EXPO_PUBLIC_ENABLE_DEMO=false`, а участникам выданы реальные тестовые аккаунты или они регистрируются сами.

## 2. Регистрация водителя

1. Водитель устанавливает APK и регистрируется как водитель.
2. В no-SMS режиме телефон подтверждается backend автоматически при регистрации; водитель подтверждает только почту.
3. Водитель заполняет правовой допуск и данные автомобиля.
4. Водитель загружает паспорт, ВУ, СТС, ОСАГО и ОСГОП.
5. Администратор проверяет карточку водителя во встроенной админке.

## 3. Проверка документов

- Если все файлы читаются, администратор нажимает `Одобрить документы`.
- Если есть проблема, администратор указывает причину и нажимает `Отклонить с причиной`.
- Доступ к файлам документов должен использовать кнопку `Открыть`; факт просмотра фиксируется backend audit.
- ОСАГО и ОСГОП проверяются как полисы, влияющие на разрешение автомобиля.

## 4. Ручной допуск и доступ

1. После проверки документов администратор нажимает `Одобрить`.
2. Затем нажимает `Открыть допуск`, чтобы закрыть договор, реестр, налоговый профиль и разрешение автомобиля в пилотной модели.
3. Затем нажимает `Активировать доступ`.
4. Backend создает ручную запись доступа с провайдером `manual-admin` и способом `Пилотная ручная активация`.
5. Если нужно снять водителя с пилота, администратор нажимает `Отключить доступ` или `Блок`.

## 5. Заказ

1. Клиент создает заказ в зоне пилота.
2. Администратор или водитель проверяет, что водитель `canReceiveOrders=true`.
3. Водитель принимает заказ.
4. При назначении заказа backend создает PIN поездки.
5. Водитель может начать поездку только после ввода PIN.
6. После завершения заказ получает финальный статус, оплату MVP и чековую запись.

## 6. Поддержка и споры

- Все обращения создаются через экран поддержки.
- Администратор видит обращения и realtime-уведомления в админке.
- Для спора по поездке проверяются заказ, PIN, статусы, водитель, клиент, история сообщений и время событий.
- При риске безопасности водитель блокируется до выяснения.

## 7. Ежедневная сверка

- Количество заказов, завершений и отмен.
- Список активных водителей и их документы.
- Обращения поддержки без ответа.
- Водители с отключенным доступом или блокировками.
- Ошибки backend и доступность LAN API.
- Ручные активации доступа и причины отключений.

## 8. Что не входит в этот срез

- Production backend с HTTPS, PostgreSQL и доменом.
- Публикация в Google Play или TestFlight.
- Прием платежей от водителей или клиентов.
- Финальная юридическая модель без проверки юристом.
