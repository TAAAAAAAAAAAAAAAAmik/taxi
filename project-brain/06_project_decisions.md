# Решения по проекту

## Принятые решения

1. Проект развивается от малого к большему.
2. Главный MVP-сценарий важнее красивых дополнительных функций.
3. Obsidian используется как база знаний проекта.
4. Codex должен читать AGENTS.md, TODO.md, DEVELOPMENT_PLAN.md и project-brain.
5. Названия файлов в project-brain сделаны на английском, чтобы PowerShell не ломался.
6. Внутри файлов можно писать по-русски.
7. Реальные платежи подключаются позже.
8. Карты и сложная логистика подключаются позже.
9. Записи состояния backend сериализованы и атомарны (temp-файл + rename), а мутации заказа идут через критическую секцию `mutateDb` (read-modify-write под замком) — чтобы убрать гонки, когда два запроса затирают изменения друг друга. Это временное решение поверх единого JSON/jsonb-документа; «навсегда» — нормализованные таблицы заказов/платежей.
10. Принятие заказа идемпотентно: повторный «принять» тем же водителем возвращает `200` (no-op с текущим заказом), а не `409`. Конфликт `409` — только если заказ уже держит ДРУГОЙ водитель. Это контракт для ретраев realtime-сети; гонку двух водителей закрывает сериализованный `mutateDb`. Forward-only переходы статусов — через `isAllowedOrderStatusTransition` (источник истины на бэке).

11. Доставка — часть клиентского MVP и должна оставаться доступной клиенту. Точки входа: на клиентской главной (`ClientHomePage` в `src/components/PostRegistrationMenu.tsx`) — две плитки «Такси» / «Доставка» (через колбэк `onOpenDelivery` → `OrderFlow` с `serviceType: 'delivery'`); внутри `src/screens/OrderFlowScreen.tsx` — переключатель «Такси / Доставка» (`serviceSwitch`). Инициализация `serviceType` уважает параметр навигации (`initialServiceType ?? 'taxi'`) — НЕ форсить `'taxi'` для роли `client`. Не удалять эти точки входа без явного решения: код доставки (`isDeliveryOrder`, delivery-шаги, `getServiceCopy('delivery')`) тогда остаётся, но становится недостижим для клиента.

12. Платёжная модель водителя (2026-06-18): комиссия/проценты убраны полностью. Доступ к заказам — «Дневной» 100 ₽ за 24 ч (`daily`, `accessDays: 1`) ИЛИ «Партнёр PRO» 2 490 ₽/мес (`monthly`, 30 дней). Источник: `src/data/subscription.ts` (`driverAccessPlans.daily` / `.monthly`, `driverDailyPrice = 100`, `driverPartnerProPrice = 2490`). Дефолт нового водителя — `daily`. В backend старые значения `commission`/`service-share` допускаются только как инертное легаси: нормализовать в `daily`, суммы 0, статус `not_applicable`; в продукте/UI процентов нет.

13. Стандарт экранов (2026-06-18): не делать «одну длинную страницу» для сложных сценариев. Использовать короткие сфокусированные экраны и шаги: один экран = одно решение пользователя. Для многошаговых потоков — общий step-rail, переход вперед `slide`, завершение/подтверждение `fade`, вход в чат или связанный объект — `slide + fade` с ощущением shared-element. Вторичные действия (история, дом, поддержка, профиль, документы, админские длинные секции) выносить в отдельные routes/экраны. Codex должен тиражировать этот паттерн при разделении `DriverDocumentsScreen`, `AdminPanelScreen`, `ReferralScreen` и длинных форм.

## Главный принцип

Не создавать новый проект с нуля.

Codex должен продолжать существующий проект и делать маленькие изменения.
