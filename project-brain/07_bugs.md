## Записи

Дата: 2026-06-15 (Claude)
Ошибка: Гонка данных в backend — параллельные запросы по одному заказу затирали изменения друг друга. Каждый запрос читал свежую копию всего состояния, менял свою часть и писал всё обратно (read-modify-write без блокировки). Двое водителей могли «принять» один заказ; оплата / смена статуса / доля сервиса теряли чужие изменения. Плюс запись db была неатомарной — краш во время записи мог оставить битый JSON.
Где появилась: scripts/mvp-backend.mjs — writeDb и PATCH /orders/:id/{assign,payment,status,offer,service-share}.
Что пробовали: сначала сериализовали только запись (writeDb через очередь) + атомарная запись (temp-файл + rename). Этого мало: readDb отдаёт каждому запросу свежую копию, и последняя полная запись всё равно затирала предыдущую.
Как решили: добавлен mutateDb(fn) — сериализованная критическая секция read-modify-write (читает свежее состояние → меняет → пишет как одна операция). Все 5 мутирующих маршрутов заказа переведены на mutateDb. Проверено 10 smoke-тестами (dispatch, driver-billing(+yookassa/tbank), realtime, referrals, verification, documents, auth-delivery, geo-messaging).
Какие файлы изменены: scripts/mvp-backend.mjs. Коммиты efc3296, d642a7a, 998b98c.

Дата: 2026-06-15 (Claude) — ИСПРАВЛЕНО
Ошибка: обработчик PATCH /orders/:id/status принимал любой nextStatus без проверки «переход только вперёд по разрешённой схеме». Были возможны недопустимые переходы (например, completed → searching) и «воскрешение» терминальных заказов.
Где появилась: scripts/mvp-backend.mjs — смена статуса заказа.
Что пробовали: —
Как решили: добавлены ORDER_STATUS_RANK + isAllowedOrderStatusTransition (ранги по схеме created→searching→accepted/assigned→arrived→started→completed/closed, плюс cancelled). Разрешены: тот же статус, движение вперёд, отмена из активного. Запрещены: откат назад, выход из терминального статуса, неизвестный статус. Ответы: 422 (недопустимый переход), 400 (неизвестный статус). Неизвестный исходный статус не блокируется (легаси). Проверено 8 smoke-тестами + unit-проверкой переходов.
Какие файлы изменены: scripts/mvp-backend.mjs. Коммит c97a198.

Дата: 2026-06-15 (Claude) — ИСПРАВЛЕНО
Ошибка: повторное «принять» заказ тем же водителем (ретрай сети / двойной тап) возвращало 409 «Order is already accepted by another driver» — хотя водитель тот же, это не конфликт, а идемпотентный ретрай. Клиент мог показать ложную ошибку «занято другим».
Где появилась: scripts/mvp-backend.mjs — PATCH /orders/:id/assign, проверка order.driver?.id.
Что пробовали: — (найдено при ревью пути принятия после консультации с Codex по идемпотентности/гонкам; долг по forward-only из 09_last_state оказался уже закрыт записью выше).
Как решили: если order.driver.id === driver.id → возвращаем 200 { order } как no-op, НЕ трогая статус (чтобы не откатить arrived/started обратно в accepted). 409 остаётся только когда заказ держит ДРУГОЙ водитель. Гонку двух водителей по-прежнему закрывает сериализованный mutateDb на свежем состоянии. Биллинг на повторный completed идемпотентен (settleOrderPayment пересчитывает дневную долю, не инкрементирует). Проверено: npm run test:dispatch, test:realtime — зелёные.
Какие файлы изменены: scripts/mvp-backend.mjs (обработчик assign).
