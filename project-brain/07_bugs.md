## Текущие заметки

Пока главная задача — проверить главный MVP-сценарий:

клиент создает заказ → водитель видит заказ → водитель принимает заказ → статус меняется → заказ завершается.

## Записи

Дата: 2026-06-15 (Claude)
Ошибка: Гонка данных в backend — параллельные запросы по одному заказу затирали изменения друг друга. Каждый запрос читал свежую копию всего состояния, менял свою часть и писал всё обратно (read-modify-write без блокировки). Двое водителей могли «принять» один заказ; оплата / смена статуса / доля сервиса теряли чужие изменения. Плюс запись db была неатомарной — краш во время записи мог оставить битый JSON.
Где появилась: scripts/mvp-backend.mjs — writeDb и PATCH /orders/:id/{assign,payment,status,offer,service-share}.
Что пробовали: сначала сериализовали только запись (writeDb через очередь) + атомарная запись (temp-файл + rename). Этого мало: readDb отдаёт каждому запросу свежую копию, и последняя полная запись всё равно затирала предыдущую.
Как решили: добавлен mutateDb(fn) — сериализованная критическая секция read-modify-write (читает свежее состояние → меняет → пишет как одна операция). Все 5 мутирующих маршрутов заказа переведены на mutateDb. Проверено 10 smoke-тестами (dispatch, driver-billing(+yookassa/tbank), realtime, referrals, verification, documents, auth-delivery, geo-messaging).
Какие файлы изменены: scripts/mvp-backend.mjs. Коммиты efc3296, d642a7a, 998b98c.

Дата: 2026-06-15 (Claude) — ИСПРАВЛЕНО
Ошибка: обработчик PATCH /orders/:id/status принимал любой nextStatus без проверки «переход только вперёд по разрешённой схеме». Были возможны недопустимые переходы (например, completed → searching) и «воскрешение» терминальных заказов.
Где появилась: scripts/mvp-backend.mjs — смена статуса заказа.
Что пробовали: —
Как решили: добавлены ORDER_STATUS_RANK + isAllowedOrderStatusTransition (ранги по схеме created→searching→accepted/assigned→arrived→started→completed/closed, плюс cancelled). Разрешены: тот же статус, движение вперёд, отмена из активного. Запрещены: откат назад, выход из терминального статуса, неизвестный статус. Ответы: 422 (недопустимый переход), 400 (неизвестный статус). Неизвестный исходный статус не блокируется (легаси). Проверено 8 smoke-тестами + unit-проверкой переходов.
Какие файлы изменены: scripts/mvp-backend.mjs. Коммит c97a198.

Дата: 2026-06-15 (Claude) — ИСПРАВЛЕНО
Ошибка: повторное «принять» заказ тем же водителем (ретрай сети / двойной тап) возвращало 409 «Order is already accepted by another driver» — хотя водитель тот же, это не конфликт, а идемпотентный ретрай. Клиент мог показать ложную ошибку «занято другим».
Где появилась: scripts/mvp-backend.mjs — PATCH /orders/:id/assign, проверка order.driver?.id.
Что пробовали: — (найдено при ревью пути принятия после консультации с Codex по идемпотентности/гонкам; долг по forward-only из 09_last_state оказался уже закрыт записью выше).
Как решили: если order.driver.id === driver.id → возвращаем 200 { order } как no-op, НЕ трогая статус (чтобы не откатить arrived/started обратно в accepted). 409 остаётся только когда заказ держит ДРУГОЙ водитель. Гонку двух водителей по-прежнему закрывает сериализованный mutateDb на свежем состоянии. Биллинг на повторный completed идемпотентен (settleOrderPayment пересчитывает дневную долю, не инкрементирует). Проверено: npm run test:dispatch, test:realtime — зелёные.
Какие файлы изменены: scripts/mvp-backend.mjs (обработчик assign).

Дата: 2026-07-12 (Claude) — ИСПРАВЛЕНО (аудит №2)
Ошибка: (1) Приватность: realtime-событие driver_chat рассылалось всем подключениям, включая сессии клиентов — пассажир мог читать чат водителей через SSE. (2) У клиента до назначения водителя показывалась демо-заглушка «Алексей, Hyundai Solaris, 4.92 · А123ВС 96» с кнопками связи — и в карточке «Водитель», и в шапке карты («4.92 · А123ВС 96 · N мин»).
Где появилась: scripts/mvp-backend.mjs (рассылка driver_chat); src/screens/OrderStatusScreen.tsx (дефолт-driver из config).
Как решили: (1) фильтр рассылки по роли сессии (isDriverLikeRole || admin) для SSE и WebSocket. (2) флаг hasAssignedDriver: у клиента без водителя — честный плейсхолдер «Ищем водителя рядом» без контактов; мета карты — «Подбираем ближайшую машину · ~N мин». Проверено Playwright: фейковых данных на экране 0, оба плейсхолдера на месте; typecheck, test:realtime зелёные.
Какие файлы изменены: scripts/mvp-backend.mjs, src/screens/OrderStatusScreen.tsx.

Дата: 2026-09-07 (Claude) — ИСПРАВЛЕНО (аудит №3, авторизация по кодам)
Ошибка: (1) КРИТИЧНО, деньги: запрос кода (/auth/verification-code, /auth/sms-login/request, /auth/password-reset/request) не имел никаких ограничений — скрипт в цикле сливал весь SMS-бюджет владельца и заваливал сообщениями живой номер. Защита была только на ввод кода (verificationMaxAttempts), но не на его отправку. (2) Деньги: MVP_SESSION_TTL_DAYS=30 — каждый активный пользователь заново получал платный код раз в месяц (~1000 SMS/мес на 1000 активных). (3) Приватность: payoutAccount (платёжные реквизиты водителя) отдавался в публичном профиле водителя. (4)(5) Гонки: PATCH /drivers/:id/location (пинг каждые ~25 с) и /avatar писали базу из устаревшего снимка запроса и могли затереть параллельное принятие заказа.
Как решили: (1) checkAuthCodeRateLimit — три рубежа: пауза 60 с между кодами на номер, 5/час и 15/сутки на номер, 20/час на IP; счётчик пишется на каждую принятую попытку (включая неизвестные номера), иначе перебор бесплатен; ответ 429 с retryAfterSeconds. Все лимиты через env. (2) TTL сессии 30 -> 180 дней. (3) payoutAccount убран из публичного профиля. (4)(5) оба эндпоинта переведены на mutateDb.
Какие файлы изменены: scripts/mvp-backend.mjs, scripts/code-rate-limit-smoke-test.mjs (новый), scripts/auth-delivery-smoke-test.mjs, scripts/verification-smoke-test.mjs, package.json.
Проверено: typecheck чист, 10/10 smoke-тестов зелёные, включая новый test:code-rate-limit.

Дата: 2026-09-08 (Claude) — ИСПРАВЛЕНО (утечка пароля админки)
Ошибка: КРИТИЧНО, безопасность. В src/state/AppState.tsx был захардкожен личный пароль владельца для входа в админку на бессерверном демо (localAdminPassword). Он компилировался в публичный JS-бандл, был выложен на gh-pages и лежит в открытом репозитории (введён коммитом 16a4673 «Personal owner password for the admin panel»). Любой человек, открывший демо-страницу, мог найти его поиском по исходникам бандла.
Как решили: пароль удалён из кода. Демо-админка теперь открывается только если при сборке задан EXPO_PUBLIC_DEMO_ADMIN_PASSWORD; без него на бессерверном демо админка недоступна. В коде оставлен комментарий, что проверка пароля на клиенте не является защитой в принципе — настоящая проверка админа живёт на сервере (/auth/admin-login, MVP_ADMIN_PASSWORD).
ОСТАЁТСЯ СДЕЛАТЬ ВЛАДЕЛЬЦУ: сменить этот пароль везде, где он использовался; старое значение остаётся в истории git и в ранее опубликованных сборках, его удаление требует переписывания истории и force-push.
Какие файлы изменены: src/state/AppState.tsx.
