# План разработки: от малого к большему

## Главный принцип

Проект нельзя сразу превращать в огромное приложение с оплатами, картами, админкой, аналитикой и маркетингом.

Сначала нужно сделать маленький, но рабочий сценарий:

клиент создал заказ → водитель увидел заказ → водитель принял заказ → статус изменился → заказ завершился.

Если этот путь работает стабильно, приложение уже можно показывать как MVP.

---

# Этап 1 — Проверка основы проекта

## Цель

Убедиться, что проект запускается и не ломается.

## Что сделать

- Проверить запуск приложения.
- Проверить основные экраны.
- Проверить роль клиента.

- Проверить регистрацию.

# Этап 2 — Главный MVP-сценарий

## Цель

Сделать главный путь приложения рабочим.

## Главный сценарий

1. Клиент открывает приложение.
2. Клиент выбирает роль клиента.
3. Клиент создает заказ.
4. Заказ попадает в список доступных заказов.
5. Водитель открывает приложение.
6. Водитель видит заказ.
7. Водитель принимает заказ.
8. Статус заказа меняется.
9. Клиент видит изменение статуса.
10. Заказ завершается.

## Что сделать

- Проверить форму создания заказа.
- Проверить список заказов для водителя.
- Добавить кнопку "Принять заказ", если её нет.
- Добавить понятные статусы заказа.
- Добавить простое хранение заказов.
- Сделать понятные сообщения для клиента и водителя.

## Статусы заказа

- создан
- принят
- водитель в пути
- поездка началась
- завершён
- отменён

## Результат этапа

Можно показать приложение и объяснить:

"Вот клиент создает заказ, а водитель его принимает".

# Правила для Codex

## Перед изменениями Codex должен

1. Прочитать AGENTS.md.
2. Прочитать TODO.md.
3. Прочитать DEVELOPMENT_PLAN.md.
4. Прочитать папку project-brain.
5. Понять текущую структуру проекта.
6. Предложить план изменений.
7. Только потом менять код.

## Как выполнять задачи

- Одна задача — один небольшой набор изменений.
- Не менять сразу 20 файлов без необходимости.
- После каждого изменения объяснять:
  - что изменено;
  - зачем изменено;
  - какие файлы затронуты;
  - как проверить результат.

## Что запрещено

- Переписывать проект с нуля без разрешения.
- Удалять рабочую логику без объяснения.
- Добавлять сложные технологии раньше времени.
- Подключать реальные оплаты на раннем этапе.
- Делать сложные карты до рабочего MVP.
- Ломать текущую сборку.

## Главный приоритет

Сначала рабочий сценарий.
Потом удобство.
Потом админка.
Потом деньги.
Потом масштабирование.
